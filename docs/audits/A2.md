# Gate A2: audit of iCloud Keychain sync

**Date:** 2026-08-14
**Scope:** the sync feature as landed in commits `1b6dd21` and `101223b`: the shared
access group, `setSynchronizable(_:)`, `SyncAwareKeychainStore`, the settings interface,
and every claim `SECURITY.md` and `docs/ARCHITECTURE.md` now make. The whole of
`Sources/OpenFactorCore` was read, about 1,900 lines. Claims from gate A1 that
`SECURITY.md` still repeats were re-checked by inspection and grep, not re-audited to A1
depth.
**Reviewer:** Claude Fable 5, in a cold session with no memory of the sessions that wrote
the code. This is the cold pass the A1 honesty note asked for, for this scope.

**The one sentence that matters.** No path was found by which secret material leaves the
device beyond what the sync switch is documented to do, and no path through the
conversion reads a secret. What this audit did find is that several statements in the
interface and the documentation are stronger than what the code, or Apple's
documentation, can support, and one of Apple's documented caveats points in the opposite
direction from the claim this repository reasons its way to.

**A limit on everything verified here.** Every observation of the sync code, the hosted
test suite, the temporary button run recorded in `handoff.md`, and this audit's own test
run, was made against a keychain that does not actually sync: a simulator with no iCloud
account. On such a keychain, `kSecAttrSynchronizable` is a stored bit, and flipping it is
a local database write. On a device with iCloud Keychain live, the same call must
interact with the sync machinery, and none of this project's evidence covers that case.
The two device experiment is not a nicety, it is the first time most of this feature will
have been observed doing what it is for.

## Verified

- **`setSynchronizable(_:)` reads no secret on any path.** The listing query sets
  `kSecReturnData` to false explicitly, the per item update writes exactly two
  attributes, `kSecAttrSynchronizable` and `kSecAttrAccessible`, and no branch touches
  `kSecValueData` or `kSecAttrGeneric`. Confirmed by reading every line of the method and
  by the hosted test that converts an account and shows its secret unchanged. Nothing was
  found in this section.
- **The conversion cannot cross wire a secret onto another account's metadata.** Secret
  and metadata live in one Keychain item, updates are atomic per item, the repair pass is
  keyed by each item's own UUID, and the conversion never writes metadata at all. The
  single item design makes the cross wiring failure unrepresentable rather than merely
  avoided. This is a real strength of the PR 4 decision and worth saying plainly.
- **A device locking mid conversion is handled.** `SecItemUpdate` on a `WhenUnlocked`
  item returns `errSecInteractionNotAllowed` while locked, which maps to
  `SecretStoreError.deviceLocked`, which the settings screen turns into "Unlock your
  device and try again." The preference is written only after the whole conversion
  succeeds, so a partial run leaves the switch showing the old value. Within one device,
  re-running repairs: the idempotency test passes, and the skip condition means converted
  items are left alone. See F13 for the cross device case, and F14 for the skip
  condition's failure mode.
- **The preference is written only after the Keychain work succeeds,** as `SECURITY.md`
  claims. `SettingsView.syncBinding` calls `setSynchronizable` first and assigns
  `syncEnabled` after. Confirmed by reading, and by the settings tests.
- **Sync is off by default** at every layer: the `@AppStorage` default, the store's
  constructor default, and the hosted test asserting a fresh account is not
  synchronizable and carries `WhenUnlockedThisDeviceOnly`.
- **An account added after the switch moves is written the way the switch says.**
  `SyncAwareKeychainStore` reads the preference per call, and
  `SyncAwareStoreTests.followsThePreferenceWithoutBeingRebuilt` proves it against a real
  Keychain with the same store instance. The handoff's file listing says `OpenFactorTests/`
  holds only `PaletteTests`; it actually holds eight test files including these. See F18.
- **The test suite passes.** 213 unit tests in 26 suites, hosted, on the iPhone 17 Pro
  simulator with `-parallel-testing-enabled NO`. The one failure in a full run is the
  template `OpenFactorUITestsLaunchTests.testLaunch`, killed by SIGTERM mid rotation; the
  launch performance test in the same target passes, so the app boots. CI excludes the UI
  test target deliberately and this failure is consistent with that decision, not with an
  app defect.
- **No network code, no logging, no third party dependencies.** Grep finds no URLSession,
  Network framework, socket, print, NSLog, os_log, or Logger anywhere in `Sources/` or
  `OpenFactor/`, and `Package.swift` declares nothing. The About footer's "makes no
  network requests of its own" is accurate, including the "of its own", which correctly
  leaves room for iCloud Keychain being the operating system's traffic. But see F16: CI
  does not verify this, and `SECURITY.md` says it does.
- **"Apple cannot read them" is supported by Apple's platform security documentation.**
  Synced items are encrypted so only devices in the user's circle of trust can decrypt
  them, and the escrow copy is guarded by HSMs that verify the passcode via SRP without
  Apple seeing it, destroy the record after 10 failures, and give Apple no read path. The
  neighbouring sentence in `SECURITY.md` is not supported: see F15.
- **"A synchronizable item cannot be device only" is Apple's documented rule,** so the
  protection class change is genuinely forced, and the footer is right to present it as
  the price of sync rather than a choice.

## The three reasoned claims

### Claim 1: turning sync off leaves the copies on other devices alone

**Not established, and Apple's documentation leans the other way.** The
`kSecAttrSynchronizable` page states: "Updating or deleting items using the
kSecAttrSynchronizable key affects all copies of the item, not just the one on your local
device." The sync off path is exactly such an update: its per item query names
`kSecAttrSynchronizable: true` and its change dictionary writes the flag to false. Read
literally, Apple says that update reaches the other devices' copies. What "affects" means
for this particular transition, demote everywhere, delete everywhere, or nothing remote,
is not documented, and community reports conflict, including a claim that moving an item
out of iCloud requires delete and re-add rather than an update. The repository's written
position, that the copies elsewhere are outside this app's control and the interface
should not claim either way, is the right posture, but `handoff.md` states the leave-alone
version as the expectation, and the sync-on footer promises "stops them reaching your
other ones", which is itself an unverified propagation claim. Settled only by the
experiment below. Until then, no document or footer should imply any remote outcome,
including the quiet one.

### Claim 2: merging is what service plus account keying implies

**The reasoning is sound and consistent with the documentation, and one corner of it is
unexamined.** Distinct UUIDs merging as a union, the same item written twice resolving to
one winner, and deletion propagating are all consistent with the primary key structure
and with Apple's caveat quoted above. Apple does not publicly document iCloud Keychain
conflict resolution in detail, so "later write wins" in `ARCHITECTURE.md` is an
assumption, though a conservative one given both copies hold the same secret. The
unexamined corner: because `kSecAttrSynchronizable` participates in the primary key, a
local item and a synced item with the same service and UUID can coexist. The off then on
cycle can construct this, see F13, and `records()` would then list one account twice.
The merge description should be confirmed by the experiment, and the twin case added to
it.

### Claim 3: a watchOS target in the same access group sees the phone's synced items

**Better supported by current documentation than the repository fears, and still
unproven for this configuration.** The current `kSecAttrSynchronizable` page lists
watchOS 2.0 in its availability and states: "Starting in iOS 14, macOS 11, and watchOS 7,
the keychain synchronizes passwords, certificates, and cryptographic keys." That sentence
has no meaning unless watchOS participates in keychain synchronization. The contrary
evidence is old: a 2017 Apple engineer post explaining that access groups stopped
spanning the phone and watch when extensions moved onto the watch, and a 2018 citation of
documentation saying the key was not available on watchOS. A 2020 first hand report
describes exactly OpenFactor's configuration working, a shared team prefixed group plus
the synchronizable flag, with items reaching the watch after a delay. So the design is
right in structure: the access group is a same device visibility mechanism, iCloud
Keychain is the transport between devices, and the two compose. What no source
demonstrates is this app's precise arrangement, generic password class,
`kSecUseDataProtectionKeychain`, the group reached implicitly as the first entitlement
entry, on current watchOS. PR 14's plan to prove it before building anything is correct
and should stand. Residual unknowns for that proof: whether the watch must have its own
passcode for `WhenUnlocked` items, and how long arrival takes.

### The experiment that settles all three

Two devices on one Apple Account, iCloud Keychain on, the app on both, plus the PR 14
watch stub. In order: enable sync on A and confirm arrival on B while B's switch is off,
which also tests the F12 premise; rename on B and confirm propagation to A; delete one
account on B and observe A, for F9; turn sync off on A and observe B's copy, which is
claim 1; turn sync back on on A and watch for duplicate rows or `errSecDuplicateItem`,
which is F13; then read the group from the watch stub, which is claim 3. Each step is an
observation this repository currently substitutes with reasoning.

## Findings

Numbered continuing from A1. None are fixed in this gate; it produces a report.

### F8: the sync off story contradicts Apple's documented caveat, and the footer promises what nobody has observed

What is wrong: `handoff.md` expects turning sync off to leave other devices' copies
alone, and the sync-on footer says "stops them reaching your other ones", while Apple's
documentation says updates through `kSecAttrSynchronizable` affect all copies. Nobody has
observed the actual behaviour, and everything observed so far ran on keychains that do
not sync at all, so even the local half of the off transition is unobserved on a live
keychain. Why it matters: a user reasons about where their irrevocable secrets are from
these sentences. If the update propagates as a removal, a user who thought their iPad
kept a copy has lost their second factor; if it propagates as nothing, a user who thought
"off" contained the secrets has copies they do not know about. Both wrong beliefs are
expensive and only one sentence can be true. What would fix it: run the experiment; until
then, reword the footer's off clause to what is known, that this device stops offering
changes to iCloud Keychain, and strike the leave-alone expectation from `handoff.md`.

### F9: the deletion confirmation is wrong when sync is on

What is wrong: the alert says "Its secret is deleted from this device and cannot be
recovered." `docs/ARCHITECTURE.md` itself says an account deleted on one device is
deleted on the others, that is what sync means, and Apple's caveat supports it: the
delete query includes `kSecAttrSynchronizableAny`, and deletion through that key affects
all copies. Why it matters: this dialog is the one place the app names the consequence
before the only irreversible act it performs. A user who keeps a second device precisely
as their fallback reads "from this device", deletes on the phone, and loses the account
everywhere, permanently, with the enrollment page long gone. The confirmation currently
understates the blast radius in exactly the situation where the user is relying on the
overstatement. What would fix it: sync aware wording, "from this device" when the item is
local, "from all of your devices" when it is synchronizable, and the experiment confirming
which one iCloud Keychain actually delivers.

### F10: the sync-on footer asserts presence in iCloud Keychain that the app cannot observe

What is wrong: "Your accounts are in iCloud Keychain" and "so they reach your other
devices" are statements of fact, but marking an item synchronizable only offers it to
iCloud Keychain. If the user has iCloud Keychain off in iOS Settings, the conversion
succeeds, the switch sits on, the footer asserts the accounts are in iCloud, and nothing
has left the device. There is no public API to check the OS level state, so the app
genuinely cannot know. Why it matters: the dangerous direction is the user who believes
their accounts are backed up. They lose the phone, expect the codes on the new one, and
have nothing, which for TOTP means re-enrolling everywhere they still can and losing what
they cannot. What would fix it: word the footer as a request rather than a fact, and name
the prerequisite: sync requires iCloud Keychain to be on in iOS Settings, and the app
cannot verify delivery. Uncomfortable and true beats comforting and conditional.

### F11: the footer promises Apple Watch, and there is no watch app

What is wrong: "so they reach your other devices, including Apple Watch" names a target
that does not exist; PR 14 has not started, and the claim additionally rests on
unverified claim 3. The settings screen's own header comment states the project rule: for
a security tool, an aspirational row is a false claim. This is an aspirational footer.
Why it matters: beyond the broken promise, it teaches the user that the watch already
holds their secrets, which shapes how they would treat a lost watch, in the wrong
direction for now and possibly the right one later. What would fix it: delete "including
Apple Watch" until the watch app ships and claim 3 is proven.

### F12: the About footer states a Keychain fact it never checks, and the divergence is real

What is wrong: with sync off, the About footer says "OpenFactor stores your accounts on
this device only." That is a statement about the Keychain keyed entirely off a
`UserDefaults` bool, and the two can disagree three ways: a conversion that failed part
way leaves some accounts synchronizable while the switch reads off; accounts synced from
another device arrive at the OS level regardless of this device's preference, are listed
by `records()` through `kSecAttrSynchronizableAny`, and edits or deletions made here
propagate outward while the footer says device only; and a user who ran sync on then off
has copies elsewhere whatever the local state says. The `SECURITY.md` reasoning for not
silently reconciling at launch holds: an arrived account is indistinguishable from a
half converted one, and "repairing" it would yank another device's account out of sync
everywhere. But that argument justifies not repairing; it does not justify not telling.
The store can already see the disagreement, the listing returns each item's sync state.
Why it matters: "on this device only" is the single strongest security sentence in the
app, and it is the one sentence the app asserts without looking. What would fix it:
either derive that sentence from the Keychain, saying "some of your accounts are synced"
when the states disagree, or weaken it to describe the setting rather than the state.
The settings footer should also say the other half of the arrival fact before the switch
is flipped: enabling sync sends the accounts to every device on the Apple Account where
the app is installed, without any action on those devices.

### F13: "running it again repairs it" is proven for one device and doubtful for two

What is wrong: the idempotency argument holds locally and is tested locally, but the off
then on cycle with a second device can construct a state re-running does not repair.
Turn sync off on A, its items become local; B's copies remain synced and can re-arrive
on A; A now holds a local item and a synced item with the same service and UUID, legal
because the sync flag is part of the primary key. Turning sync on again updates the local
twin toward a primary key that already exists, which should return `errSecDuplicateItem`,
thrown as a generic "try again" that will fail identically every time, while `records()`
draws the account twice. Why it matters: the repair claim is written in `SECURITY.md` as
the reason the partial failure mode is acceptable, so a state that defeats the repair
needs to be known about, especially one reached by an ordinary off then on sequence. What
would fix it: include the cycle in the experiment; if the wedge is real, resolve the twin
deliberately, for instance by preferring the synced copy and deleting the local one,
which risks at most a rename, never a secret. Separately, the single device half of the
repair claim is testable today and untested: no test builds a mixed state, some items
converted and some not, and asserts a re-run converts exactly the unconverted remainder
while leaving the others' metadata intact. The existing idempotency test only re-runs a
fully converted store. That is the load bearing assertion behind "try again", and it is
missing.

### F14: the conversion's skip condition fails silent in the dangerous direction

What is wrong: `(item[kSecAttrSynchronizable as String] as? Bool) ?? false` decides
whether an item needs converting. If that read ever fails, wrong bridged type, missing
attribute, the item is assumed local. Turning sync on then fails loudly, the update
matches nothing and throws. Turning sync off skips the item silently: it stays in iCloud
Keychain while the switch, the footer, and the About text all say device only. Why it
matters: the asymmetry means the failure that overstates exposure is loud and the failure
that understates it is silent, which is backwards for a security tool. The bridging works
on today's simulator, the tests prove that much, but the invariant deserves better than
a default. What would fix it: put the selection in the query instead of the loop, list
with `kSecAttrSynchronizable: !shouldSync` so the Keychain itself returns exactly the
unconverted items and no parsing is needed, or treat an unreadable sync state as an error
rather than a guess.

### F15: "never leave your devices" is contradicted by Apple's own escrow design

What is wrong: `SECURITY.md` says "The keys are derived from your device passcodes and
never leave your devices, so Apple cannot read the synced items." Apple's platform
security guide says the random keys that encrypt the keychain are escrowed with Apple,
guarded by HSM clusters that verify the passcode through SRP, permit 10 attempts, and
destroy the record after failure. "Apple cannot read them" survives, and the escrow is
why recovery works with all devices lost. "Never leave your devices" does not survive,
and the escrow path is also the sharpest real attack: an attacker with the iCloud
password, control of the trusted phone number, and a guessable device passcode recovers
the keychain with none of the user's devices, inside 10 guesses. The existing attacker
paragraph is close, it names iCloud password plus a device passcode, but it describes
joining the circle from a new device, and the escrow route needs the SMS leg named too.
Why it matters: this document's stated bar is claims no stronger than the facts, and
this one is stronger than Apple's own description. It also hides the one user
controllable defence: a strong alphanumeric device passcode strengthens exactly this
path. What would fix it: name the escrow, keep "Apple cannot read", and state the
recovery route attack alongside the circle of trust one.

### F16: SECURITY.md says CI verifies the no network claim, and CI does not

What is wrong: "The app makes no requests, so there is nothing to intercept. This is
verified in CI rather than asserted, see PR 17." The CI workflow contains style checks,
project setting greps, and the two test jobs. Nothing inspects for network code. The
claim is true, this audit verified it by grep, but the sentence about how it is verified
is false today. Why it matters: the document's credibility rests on the verified and
planned markers meaning what they say; this sentence launders a plan into a present
tense fact, exactly what the *planned* convention exists to prevent. What would fix it:
either add the grep to CI now, it is four lines next to the em dash check, or write
"will be verified in CI in PR 17".

### F17: the plaintext export "out of scope" entry describes a feature that does not exist

What is wrong: "Your own choice to export secrets in plaintext, which the app permits
behind an explicit warning" is present tense; there is no export of any kind until
PR 16. Why it matters: small, but the document defines its own rule, claims marked
planned are not yet true, and this claim is unmarked. A reader auditing the app against
this document goes looking for an export warning that is not there. What would fix it:
mark it planned, one word.

### F18: two documents describe the access group design backwards or stale

What is wrong: the `accessGroup` doc comment in `KeychainSecretStore` says the group is
"Named explicitly rather than left to the default", while the app deliberately passes
nil and relies on the first entitlement group, which `OpenFactorApp` and the commit
message describe as the design, and which the hosted test asserts works. An auditor
reading the core alone is told the opposite of what ships. Separately, `handoff.md`'s
file listing says `OpenFactorTests/` is an empty folder holding only `PaletteTests`; it
holds eight files, including the sync store and settings suites this audit relied on.
Why it matters: both documents exist so that a cold reader gets the truth without
archaeology; both currently mislead one. What would fix it: reword the doc comment to
describe the entitlement default mechanism, and regenerate the handoff listing.

## Positions taken on rejected alternatives

Reviewed as `docs/ARCHITECTURE.md` asks. CloudKit for secrets: rejection agreed, iCloud
Keychain's end to end guarantee is stronger by default than CloudKit encrypted fields.
WatchConnectivity for the watch: rejection agreed given claim 3's documentation support;

### The new surface

**The migration, `migrateToDefaultAccessGroup()`, held to the same standard as
`setSynchronizable`.** No path reads secret data: the listing sets `kSecReturnData` false,
the probe that discovers the default group carries no value at all and is deleted in a
`defer`, and the per item update writes only `kSecAttrAccessGroup`. That `SecItemUpdate`
can move an item between groups without the secret being touched is proved by test rather
than assumed, which is exactly the discipline the audit asked for. Partial failure is
re-runnable: the update is in place, items already in the target group are skipped, and it
runs again at next launch. Cross wiring remains unrepresentable for the same single item
reason as before. The concerns that survive are F20 and F21 below, plus one member of the
F8 family: moving an already synchronizable item between groups is an update through a
query that names `kSecAttrSynchronizable`, so Apple's "affects all copies" caveat applies
to it as much as to the sync switch, and what that does remotely is as unestablished here
as there. It was observed to work once, on the author's own phone and watch pair.

**The watch app is read only in fact, not just in intent.** `WatchAccountListView` calls
`records()` and nothing else; `WatchCodeView` calls `secret(for:)` at the moment a code is
drawn and holds neither the secret nor a stale code. The stale code fix is sound by
construction: the clock is never stored, `TimelineView` supplies it at render, and the
held code is drawn only while it belongs to the window that clock is in, so returning
state cannot show a previous visit's code. A counter based account shows "unavailable"
rather than a code, which is correct twice over: advancing a counter is a write, and a
write from the watch would fork the count. The store's write settings are irrelevant
because nothing on the watch writes, which was checked rather than taken from the comment.

**The complication holds nothing, and the absence is verifiable.** The target has no
`CODE_SIGN_ENTITLEMENTS` in the project file, imports only SwiftUI and WidgetKit, and its
timeline is one entry with a `.never` policy, so it has no reason to wake near secret
material. `docs/PROJECT.md` records the absence as the guarantee. Agreed: a live code on a
watch face would be a second factor shown to the room, and this design refuses it
structurally. One suggestion: the CI project settings job asserts presence of strings and
cannot see this absence; asserting that `CODE_SIGN_ENTITLEMENTS` appears exactly four
times in the project file would turn the guarantee into a checked one.

**The DEBUG rehearsal mode is compiled out of release, agreed.** Both the launch argument
check and the fake store builder sit inside `#if DEBUG`, so no release binary contains the
branch, and in a debug build it additionally requires `--layout-rehearsal` on the command
line, which nothing but a developer harness supplies. The fakes use the RFC test vector
secret, which protects nothing by design. The mode is documented in `docs/UI_SPEC.md`.

**Hardware observations, taken as the author's testimony rather than re-verified.** Claim
3 of the audit, that a watch target in the shared group sees the phone's synced items, has
now been observed on a real Apple Watch Ultra, which is consistent with the documentation
evidence gathered above. The half hour propagation of seven items is recorded in
`docs/ARCHITECTURE.md` as a design constraint and the watch's empty state is written for
it. Claims 1 and 2 remain observation free: the two device experiment in this report has
still not run, and nothing in PR 14 substitutes for it.

### New findings

**F19: the CI network and logging grep misses three shipping directories.** The pathspecs
are `Sources/*.swift`, `OpenFactor/*.swift`, and `OpenFactorTests/*.swift`.
`OpenFactorShared/`, `OpenFactorWatch Watch App/`, and `OpenFactorWatch Complication/` are
shipping code and match none of them, and all three were added in the same pull request
that added the check. `SECURITY.md` says the job "greps the whole source tree", which
overstates it in exactly the way F16 was about. Why it matters: the watch is the newest
code and the likeliest place a future convenience reaches for the network, and it is the
one place the net does not cover. Fix: grep every `*.swift` in the repository and keep the
single GitHub URL exclusion, or add the three missing pathspecs; either is two lines.

**F20: the migration fails silent in the direction the app cannot see.** Three things
compound. The per item find reintroduces `(item[kSecAttrSynchronizable] as? Bool) ??
false`, the exact pattern F14 removed from `setSynchronizable` in the same commit that
wrote this method; a flag that fails to bridge makes the find match nothing and the whole
migration throw. The call site swallows every error with `try?`, on the stated reasoning
that the phone loses nothing, which is true and phone centric: the cost of a permanently
failing migration is a watch missing accounts with no error anywhere, the exact symptom
the method's own doc comment calls the worst shape a bug can take in an authenticator. And
the loop aborts on the first per item failure, so one wedged item silently strands every
item behind it. `syncState()` carries a milder relative of the same pattern: a flag that
fails to bridge classifies the account as local, which would let the About footer say
"on this device only" about a synced account, the understating direction again. Why it
matters: every silent failure here understates where secrets are or hides that the watch
is out of sync. Fix: list synced and local items with two pinned queries instead of
parsing, in both `migrateToDefaultAccessGroup` and `syncState`; let the migration continue
past a failed item and report what moved; and surface placement somewhere, for which
`placements()` already exists and currently has no caller outside the core.

**F21: the end to end migration test never migrates anything.** The capability test proves
raw `SecItemUpdate` can move an item between groups. The end to end test named "Accounts
left in the old group are moved, and their secrets survive" writes both accounts through
the store, which lands them in the shared group, and then asserts the migration returns
zero: it exercises only the no-op path, while its name claims the load bearing one. The
missing assertion is constructible today in the hosted harness, because the capability
test already writes into the legacy group under an explicit `kSecAttrAccessGroup`: seed
one item there under the store's service, run `migrateToDefaultAccessGroup()`, and assert
one moved, still listed, secret intact. Why it matters: the migration runs at every launch
with its errors swallowed, so the test suite is the only place its main path is ever
checked, and today it is not. Fix: add that test; the pieces all exist.

Two lines of housekeeping, not numbered: the doc comment that begins "Only the two values
this app has a use for" now sits above `ItemPlacement` rather than `SecretAccessibility`,
which will attach it to the wrong declaration in generated documentation; and the watch
empty state speaks to the user who just enabled sync but only implies, rather than says,
that a user who never enabled it needs to turn it on on the phone.
