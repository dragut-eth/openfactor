# V2, first external review: ChatGPT on `docs/VAULT.md`

Verdict: approve the architecture, do not freeze the document. Six findings raised as blocking.
Its summary of the central model is the one this project would want an auditor to reach without
being told: *Keychain is storage and transport, not the confidentiality boundary.*

Assessed below with a disposition for each, because a review is not a to-do list until somebody
has judged it.

## Accepted, and the sharpest one first

**C1. The watch exchange is not a complete protocol. Accepted, blocking.**

`VAULT.md` says "ECDH → HKDF → AES-256-GCM seal to the watch's public key" as though that were
a single primitive. It is not. ECDH needs a private key on both sides, so the phone must
generate its own ephemeral keypair and return its public half; what the document describes is
ECIES with half of it missing. An implementer would have discovered this immediately, which is
not the point: **a document that claims the code is wrong whenever they disagree cannot leave
the protocol to the implementer.**

The review's additions are right and go further than the gap:

- the phone generates an ephemeral P-256 keypair per exchange and sends its public key back
- a request nonce, generated by the watch, which the design had no replay protection without
- **the transcript is bound**: protocol version, nonce, and *both* public keys go into the HKDF
  context and the AES-GCM AAD, rather than treating the shared secret as sufficient

**C3 and C4. The record formats are not normative. Accepted, blocking.**

The document calls itself normative and then defines the account record conceptually. Compare
`BACKUP_FORMAT.md`, which pins every byte and publishes test vectors. The review's phrasing is
the correct diagnosis: otherwise **the first implementation becomes the specification by
accident.**

One qualification, so this does not get gold-plated. The archive is an interchange format whose
whole purpose is that a stranger's implementation can read it, which is why it is pinned to the
byte and carries vectors verified by three implementations. The vault is internal. The bar it
must clear is that *our* implementations agree across versions and platforms and that a v2
reader can still open v1 records, not that an unrelated program can. So: exact encoding, field
order, AAD bytes, padding buckets, size limits and unknown-field behaviour, with test vectors,
and no obligation to make it independently implementable.

**C5. The wrapped key's sync semantics are ambiguous. Accepted, major rather than blocking.**

The document states that the vault key never syncs and that a sync-off device is unrecoverable
if lost, which together imply the wrapped key follows the user's sync preference, but never says
so. Recovery behaviour is the last place to leave an implication.

**C6. There is no way to tell a wiped vault from an empty one. Accepted, and improved on below.**

Correct and valuable: a sibling can delete every item, sync propagates it, and the app currently
has no way to distinguish that from a user who has no accounts. "Your vault is empty" would be
the app confirming an attack as normal.

## Accepted with a change of mechanism

**Where the manifest lives, the review has it in the wrong place.** It proposes an encrypted
manifest sealed under the vault key, which means another Keychain item, which the same attacker
deletes with everything else. A tripwire an attacker can remove is not a tripwire.

**The manifest belongs in the container**, which E4 measured to be beyond a sibling's reach.
That turns it from an inventory into an anchor: the attacker can destroy the Keychain contents
but cannot touch the record of what should have been there, so deletion becomes detectable
rather than plausible. Holding a per-account revision or hash there also detects the **replay**
the review correctly identifies as otherwise unsolved, since a rolled-back ciphertext no longer
matches what the container remembers.

**And the honest problem with that, which needs designing rather than asserting.** With sync on,
another device legitimately adds and removes accounts, so this device's container manifest goes
stale and would cry wolf. A workable shape is probably a container anchor that records only
that *a vault exists* and its high-water mark, with the detailed manifest synced and sealed, so
that total destruction is unambiguous even though individual churn is not. That is a design
question this document has not answered and should not pretend to.

## Accepted as conditional

**C2. A human-verifiable provisioning code.** A short value derived from the transcript, shown on
both screens, so the person approving on the phone knows which watch key they are approving.

Worth doing **if** the routing probe comes back showing WatchConnectivity is not exclusive to the
paired counterpart app. If it is exclusive there is no party to be confused with and the code is
ceremony. Since that probe is still outstanding, the review is right that the conservative rule,
explicit approval on the phone, stays either way.

## What this review did not cover

Not a criticism, but worth recording so the coverage is visible: it is a protocol and format
review and did not touch the operational half. The migration tripwire, the two indistinguishable
passphrases, the watch's empty state gaining a third cause, and the bootstrap race between a
correct passphrase and a wrapped key still in flight all came from the V1 round and are
unaddressed here. Both halves are needed and neither substitutes for the other.

## Disposition

**All six are now in `VAULT.md`**, revised once at the end of the round rather than three times
during it.

One disposition here was later overturned. C2, the human-verifiable provisioning code, was
accepted only *conditionally*, pending the routing probe. Fable's review argued that the point
of adding it is precisely that the claim stops depending on how that probe turns out, which is
right and better reasoning than the conditional. It is in the design unconditionally.
