# V1: the vault design, audited before it was built

Two independent cold reviews of `docs/VAULT.md`, run against the first draft, by a different
model from the one that wrote it, with no contact between them. One was given the cryptography
and key management; the other was given operational correctness and data loss and told
explicitly not to review the cryptography.

**Twelve findings accepted, five of them blocking.** Three of the blocking five were data loss
rather than weakness, which is the argument for auditing a page instead of a diff: the draft
read as finished, and would have shipped a silent erase.

## Blocking

**B1. The passphrase was persisted in the container for no reason.** The draft's key table said
"a copy in the container", and both reviewers attacked it independently. Neither recovery path
ever reads it back, it had no stated lifecycle, and it would ride into device backups, which
would have made the document's own claim, that a compromise of iCloud Keychain yields only
sealed blobs, false. **Fixed:** the passphrase is generated, displayed, acknowledged and
forgotten. Because the vault key lives in the container, a passphrase can be replaced at any
time by rewrapping, which covers the interrupted-onboarding case the copy was reaching for.

**B2. Migration would silently erase a stranger's accounts.** The draft said old plaintext items
are erased, justified by only two people holding disposable test data. Nothing in it was scoped
to those two people, and the same path would fire un-warned on whoever installed next, in an app
whose erase feature is gated behind Face ID and a typed word. **Fixed:** plaintext items are
never removed without the same deliberate confirmation, with an export offered first.

**B3. The passphrase would never have been shown to a user who keeps sync off.** The draft tied
the display to enabling sync, while the vault is created at first launch regardless. A
local-only user would hold a vault whose passphrase they had never seen, and lose everything
the first time they reinstalled. **Fixed:** the passphrase is shown when the vault is created.

**B4. The wrapped key and its salt were two records.** "Stored beside" meant two independently
syncing Keychain items, and this project has measured iCloud Keychain delivering one item at a
time over roughly half an hour. A device holding one and not the other would report a correct
passphrase as wrong. **Fixed:** version, salt, iteration count and wrapped key are one sealed
structure in one item.

**B5. Integrity and availability were never addressed.** The draft closed confidentiality
against a sibling app and said nothing about the same app's ability to *write*: deleting every
item, which sync then propagates to every device, or replaying an older ciphertext, which
verifies because nothing binds a ciphertext to a point in time. **Fixed by disclosure**, since
no key hierarchy addresses it: the limitation is stated plainly and the encrypted export is
named as the backstop rather than a convenience.

## Major

**M1. A custom vault passphrase would have reopened the key commitment collision.** The draft
inherited the archive's rules including its custom passphrase option, which implies trying
several candidate derivations against one ciphertext. That is the shape that produced the
demonstrated collision in `BACKUP_FORMAT.md`, and its fix there, requiring the plaintext to
parse, has no equivalent for 32 opaque bytes. **Fixed:** the vault passphrase is always
generated, so one form is derived and the question does not arise.

**M2. The iteration count was hardcoded.** Raising it later would have failed to unwrap every
existing vault. **Fixed:** stored in the item and clamped to the range the archive enforces.

**M3. The watch exchange had no human in the loop**, and the assumption that WatchConnectivity
routing is exclusive to the paired counterpart app was never listed as needing proof, despite
having the same shape as the assumption E1 destroyed. **Fixed:** a person taps to approve on the
phone, and the assumption is now item 2 of what must be proven.

**M4. Ciphertext length leaked issuer and account name lengths**, since GCM output is the length
of its input. **Fixed:** payloads are padded to fixed buckets before sealing.

**M5. Item count and OS timestamps are readable and were not disclosed.** The draft claimed only
a constant service string and an opaque UUID remained visible. **Fixed by disclosure.**

**M6. The bootstrap could not tell an absent wrapped key from a wrong passphrase**, so a user on
a new device would be told their correct passphrase was wrong while a record was still in
flight. **Fixed:** absent is reported as not yet arrived.

**M7. A watch asking a phone that has no key itself** was unspecified, which is the ordinary case
when both are replaced together. **Fixed.**

**M8. The watch's empty state would have misdirected.** It distinguishes two causes, accounts in
flight and sync turned off, and this design adds a third: provisioned with ciphertext arriving
but no vault key. The existing second branch tells the wearer to check sync, which would not
help. **Recorded** as an interface obligation.

**M9. "The passphrase always works" was false with sync off**, where the wrapped key exists only
on the lost device. **Fixed:** stated, with the export named as the only copy for that
configuration.

**M10. Two identical-looking passphrases.** The vault and archive passphrases are generated the
same way and displayed the same way, and somebody recovering months later holds two strings and
no way to tell them apart. **Fixed:** both must be labelled where shown and where asked for.

**M11. The vault key file's location and protection class were unspecified**, and iOS purges
`Caches` and `tmp` under storage pressure with no user action, which would have made the
durability assumption silently false. **Fixed:** `Application Support`, strongest protection
class, excluded from backups.

## Minor, all accepted

Fresh salt and nonce on rewrap and not only on creation. An HKDF info string and an AAD for the
watch exchange, for domain separation. An explicit ban on iCloud Drive and ubiquitous containers
for key material. Quick Start migration added to what must be tested, since it is a different
mechanism from backup restore and may not honour the exclusion flag. A version in the per-account
AAD so a future format change has a clean signal.

## What the reviews checked and did not object to

The central move, ciphertext in the Keychain and key in the container, was examined by both and
neither found a flaw in it. The key hierarchy has no circularity and no shortcut from the
wrapped blob to the vault key without the passphrase. The UUID as AAD correctly defeats
ciphertext swapping between accounts. A fresh ephemeral keypair per watch exchange means no
static key reuse. "Phone replaced but watch kept" was traced and holds: the watch keeps
generating codes throughout. Restoring an old device backup does not resurrect stale vault state
for a synced user, because Keychain items re-sync live. The import preview's duplicate detection
needs no change, since the `SecretStore` contract is unchanged. The complication holds neither
key nor entitlement in both the current settings and the new invariants.

## What this round could not settle

Everything under "what must be proven" in `docs/VAULT.md` remains open, and two items were added
by this round rather than removed: WatchConnectivity routing exclusivity, and Quick Start
migration behaviour. A design review cannot answer them; probes can, and they should run before
implementation rather than after.
