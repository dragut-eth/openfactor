# Gate A1: audit of OpenFactorCore

**Date:** 2026-08-14
**Scope:** the whole of `OpenFactorCore` as of the end of PR 4: Base32, HOTP, TOTP,
`otpauth://` parsing and serialization, and Keychain storage. About 1,600 lines.
**Reviewer:** Claude Fable 5, reviewing code written by Claude Opus 5.

**Honesty note on independence.** The reviewing model is different from the writing model,
but the review ran in the same session and therefore inherited the conversation's context
and reasoning. That catches a different class of mistake than the writer would, and it is
not a cold review. A genuinely cold pass costs nothing: open a fresh session on this
repository and ask for an adversarial review of `Sources/`. Recommended before tagging a
release, and the findings below should be read with that limitation in mind.

## Verified

- **RFC 4648 section 10, RFC 4226 Appendix D and section 5.4, and RFC 6238 Appendix B
  were fetched from the IETF today and compared against the committed vector tables by
  reading, not by running the tests.** All values match: 7 Base32 vectors, 10 HOTP values,
  the truncation example (`0x50ef7f19`, consistent with the RFC's mod 10^6 value 872921),
  and all 18 TOTP rows including the 20, 32, and 64 byte per algorithm seeds.
- **The one documented RFC deviation is licensed by the RFC.** Section 3.5 says decoders
  "MAY choose to reject" non zero pad bits, so accepting them is conforming decoder
  behaviour, and the encoder sets pad bits to zero as the specification requires.
- **No secret material can reach a log,** because there is nothing to reach: no `print`,
  `NSLog`, `os_log`, `debugPrint`, `dump`, or `Logger` anywhere in `Sources/`. `OTPAccount`
  conforms to neither `Codable` nor `CustomStringConvertible`, no string interpolation
  touches a secret, and `Data`'s own description prints a byte count, not contents.
- **No force unwraps, `try!`, or `as!` in `Sources/`.**
- **Fuzzing, 17,000+ deterministic iterations, now a permanent part of the suite**
  (`FuzzTests.swift`): random strings against the Base32 decoder, random bytes round
  tripped through encode and decode, valid URIs under random character mutation, random
  garbage at the parser, and randomly built accounts round tripped through serialization.
  No crash, no hang, and nothing that parses is ever partially populated.
- **The Keychain layer's queries match its claims.** Listing sets `kSecReturnData` to
  false, only `secret(for:)` requests data, the visible label is a constant, and no method
  can write a secret through the update path.

## Findings

### F1, fixed: `TOTP.counter` crashed on far future dates

`UInt64(seconds.rounded(.down))` traps when the value exceeds `UInt64.max`, so a `Date`
past roughly year 584 billion crashed the process, contradicting the function's own
stated contract of staying defined on absurd clocks, which its pre epoch guard already
honoured at the other end. Not attacker reachable: the date comes from the system clock or
a caller, never from a QR code. Verified by reproduction before fixing. Fixed with a
saturating conversion, and the regression test covers `1e19` through
`greatestFiniteMagnitude` and `Date.distantFuture`.

### F2, fixed: an unknown colour name blocked the entire account list

`AccountColor` decoded strictly, so a record written by a future version with a larger
palette would fail to decode on this one, and `KeychainSecretStore.records()` turns one
unreadable record into a failure of the whole list. Every account invisible over a paint
colour. Fixed: an unknown colour name now decodes as the default. The asymmetry with the
generator settings is deliberate and now documented at the type: an unknown algorithm
changes the codes and must keep failing loudly, an unknown colour changes a tint.

### F3, recorded and accepted: one unreadable generator still blocks the list

After F2, a record whose generator metadata cannot be read, meaning an unknown algorithm
name or a corrupted record, still fails `records()` wholesale rather than per record. This
is retained deliberately: guessing generator parameters produces plausible codes that are
rejected everywhere, and silently hiding the record loses an account without telling
anyone. The correct behaviour, surfacing "this account needs a newer version" per record,
needs an interface to surface it in, so it is deferred to the list view model in PR 7. A
schema rule is added to `ARCHITECTURE.md` to keep the case unreachable in practice: new
metadata fields must be optional with a default, and any change that alters code
generation requires a migration, never a fallback.

### F4, recorded for a later PR: HOTP counter advancement does not exist yet

Nothing increments a counter based account's counter today. Whichever PR implements it
must use checked arithmetic at `UInt64.max`, must persist the new counter before showing
the code, and must go through a store method that can do both atomically, not through
generic metadata update. Recorded here so the requirement is written down before the code.

### F5, recorded and accepted: secrets are not zeroed after use

A secret is read into a `Data`, used to generate a code, and released. Swift offers no
reliable way to zero memory that has been copied by value, and every Swift authenticator
shares this limitation. The mitigation is structural and already present: secrets are read
one at a time, for one code, and no long lived object retains one. Accepted, and worth
restating in the PR 17 threat model.

### F6, closed in PR 5: the Keychain protection class is now verified by test

Was the one item this gate could not close. The six tests asserting protection class, sync
flag, label hygiene, service isolation, and no-data listing are skipped in an unsigned test
bundle, so they proved nothing.

PR 5 added an app hosted test target and attached the existing suite to it, so the same
files now run in both contexts: unsigned under `swift test`, where the Keychain tests skip,
and inside a real app under `xcodebuild test`, where they execute. **All six pass against
the data protection Keychain**, confirming that a stored secret is written with
`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, that sync is off unless asked for, that
listing accounts returns no secret material, and that the visible label does not name the
account. The shared behaviour suite now runs against the real store too, not just the in
memory one: 407 test cases hosted, none skipped.

**Gate A1 is fully closed.**

## Addendum: `/security-review` pass, same day

After the first push, the Claude Code `/security-review` tool ran over the full branch
diff, using a separate agent with no memory of this session, followed by the false
positive filtering step it prescribes. **Zero HIGH or MEDIUM findings.** It independently
re-verified the truncation bounds, the totality of the parser, the serializer's escaping
against parameter smuggling through a crafted issuer or name, the Keychain query
construction, and the absence of any logging path.

It also surfaced one accuracy correction, adopted: the claim that metadata is encrypted
"for the same cost" as the secret overstated it. Keychain attributes, where the metadata
JSON lives, are encrypted under the keychain's own key, not the per item accessibility
class that protects the secret. Encrypted at rest and absent from unencrypted backups,
but a weaker guarantee than the secret gets. The doc comment in `KeychainSecretStore`
now says exactly that, and the PR 17 threat model must too.

F7, recorded: this distinction carries to PR 17 alongside F5.
