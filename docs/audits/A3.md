# Gate A3: audit of the backup format

**Date:** 2026-08-15
**Scope:** `docs/BACKUP_FORMAT.md` as it stands on `pr-16-backup-format` at `a14d255`, in
its entirety. There is no implementation, deliberately, so this gate audits a document:
every finding is against sentences, and every fix is an edit. The threat model in
`SECURITY.md` and the standards set in gates A1 and A2 were read for context; nothing else
was in scope.
**Reviewer:** Claude Fable 5, in a cold session with no memory of the sessions that wrote
the document. No reference implementation was consulted, because none exists, and that is
the point: the first exercise below is the document's own stated test, an implementation
written from the page alone.

**The one sentence that matters.** The cryptographic design is sound and the arguments for
it survive attack, but the test vector, the one part of this document an implementer is
told to trust above everything else, was produced by feeding the KDF the display form of
the passphrase, hyphens included, in direct contradiction of the document's own normative
rule, so every implementation that reaches "exactly these bytes" has necessarily built the
bug the rule exists to prevent.

**Verdict: not yet safe to make permanent.** Two findings block freezing the format: the
test vector contradicts the passphrase rule (F22), and the example passphrase the vector is
built on cannot be produced by the generator the document specifies (F23). Both are defects
in the document's facts, not in its design, and both are cured by one regeneration of the
vector plus a paragraph specifying passphrase entry (F24). With those three applied, and
the smaller findings at the author's judgement, this format is fit to freeze. Nothing
structural needs to change: the container, the KDF choice and its argument, the AEAD, the
AAD binding, the payload rules, and the versioning boundary are all right or repairable by
wording. This gate exists precisely because a vector like F22's, shipped, would have been
unfixable: a version 1 reader written honestly from the page and a version 1 reader
certified against the vector would disagree about which archives open.

## Verified

- **A decryptor written from this page alone opens an archive.** About eighty lines of
  Node, using only the built-in OpenSSL binding, written before reading anything else in
  the repository. Against a corrected vector (below) it produces the exact 151 plaintext
  bytes from the passphrase typed with hyphens, without them, in lower case, and with
  spaces, and refuses a file whose `iterations` reads 99,999. The document is close to
  implementable from cold; the places where it is not are F22, F24, and the inference list
  below.
- **The published test vector is internally consistent, and consistent with the wrong
  rule.** The ciphertext opens, the tag verifies, the AAD checks, and the plaintext matches
  the printed 151 bytes exactly, under the published key `7d5178…f9eb`. That key was
  re-derived here by three implementations, Python's `hashlib`, the OpenSSL command line
  KDF, and Apple's CommonCrypto, and all three agree it is PBKDF2 of
  `K7M2-9QXP-4RTV-8LZW-3NBY-6HFD`, the hyphenated display string. PBKDF2 of the stripped
  24 characters the vector's own table names as "the passphrase as fed to the KDF" is
  `f6e16618648164db0c20f92b2b29e569ff3ff6133aa78b43a3f0ed47984fe0de`, under which the
  published ciphertext refuses. See F22.
- **The AAD binding is real, not asserted.** Decrypting the published ciphertext with the
  correct key and the AAD changed to `openfactor.backup.v2`, or to nothing, fails the tag.
  A relabelled file genuinely does not open.
- **The base64 fields decode to the stated bytes and lengths.** Salt to `00…1f`, 32 bytes;
  nonce to `a0…ab`, 12 bytes; tag 16 bytes; ciphertext 151 bytes, equal to the plaintext
  length, which settles bit-exactly that the tag is carried separately and not appended.
- **The entropy arithmetic holds.** 120 bits is 15 bytes is exactly 24 Base32 characters
  with no padding, displayed as six groups of four. The claim is correct as specified. The
  example is not producible by that specification, which is F23.
- **The Base32 alphabet claim matches RFC 4648, fetched today.** Section 6's alphabet is
  `A`–`Z` and `2`–`7`; the digits 0, 1, 8, and 9 do not appear, exactly as the document
  says two lines before its example violates it.
- **600,000 iterations is still the OWASP recommendation for PBKDF2-HMAC-SHA256 as of
  today**, checked against the current Password Storage Cheat Sheet rather than remembered.
  "At the time of writing" is true and correctly hedged, since `iterations` is read from
  the file and can rise without a version.
- **The required and optional payload fields split exactly along the gate A1 line.**
  `type`, `secret`, `algorithm`, `digits`, `period`, `counter` all change generated codes
  and all fail loudly per account; `issuer`, `name`, `color`, `sortIndex` cannot change a
  code and all fall back quietly. Cross-checked against A1's F2 and F3, which set the rule.
  One account failing does not fail the archive, and unknown fields are ignored. The split
  is correct and nothing was found in it beyond the edge cases in F32.
- **PBKDF2's universal availability claim spot-checked.** Python `hashlib`, Node's
  `crypto`, the OpenSSL CLI, and CommonCrypto all produced it here without installing
  anything. One caveat lands on `SECURITY.md`, not this document: CryptoKit has no PBKDF2,
  so PR 16 will need CommonCrypto, and the practices line "All cryptography comes from
  CryptoKit" becomes false the day PR 16 lands. Noted in housekeeping.

## The decryptor exercise, and where inference replaced reading

The document's stated test is that an implementer holding only this page reaches the
vector's exact bytes. Attempted honestly, in Node against OpenSSL, then cross-checked with
CommonCrypto and CryptoKit. Everything a mainstream library needs is present: algorithm
names, key length, nonce and tag lengths, base64 dialect, AAD bytes, tag-before-parse
ordering. These points required inference the page does not license:

1. **The case fold.** "Should accept either case" has only one implementable meaning, fold
   to upper before the KDF, because the KDF consumes bytes and the canonical form is upper.
   The document never says which case is canonical or that folding happens at all. A reader
   that feeds a lower-case transcription as typed derives a different key. Part of F24.
2. **The two-candidate trial.** Generated passphrases are stripped and folded; user
   passphrases are verbatim; the file does not record which was used; and the document's
   one instruction, "a reader must try the passphrase as given", would fail every generated
   passphrase typed with its hyphens. The only strategy that satisfies all four sentences,
   try as given and then try normalised, is nowhere stated, nor is its order. Two readers
   resolving this differently disagree about which archives open. Part of F24.
3. **Length enforcement.** The 32, 12, and 16 byte lengths appear only as comments in the
   schema sketch. Whether a reader must refuse a 16-byte salt or an 8-byte nonce from some
   other writer is unstated. For salt it does not matter. For nonce and tag it does: GCM
   with a non-12-byte nonce is a different computation some libraries will happily perform,
   and a short tag is a weaker tag. Part of F27's fix.
4. **The tag's position.** Inferable, and confirmed by the vector's lengths, since 151
   ciphertext bytes for 151 plaintext bytes leaves nowhere for the tag to hide. An
   implementer with a combined-buffer library learns to append it themselves. No finding.

Could a competent implementer build something that appears to work but is subtly wrong?
Yes, and the sharpest route is the vector itself: an implementer who debugs until they
reach the published bytes has been steered into feeding the KDF hyphens, F22, and their
reader then refuses every archive written by a conforming implementation. The second route
is passphrase entry, F24, where two defensible readings diverge silently. The classic
failures the prompt names are otherwise well fenced: key truncation is precluded by the
explicit 32; parse-before-verify is explicitly forbidden, and forbidding it also covers the
streaming-decrypt trap where plaintext is consumed before the final tag check; nonce reuse
is precluded for readers and stated for writers, though in the wrong place, F25.

## The cryptography

### The PBKDF2 argument, attacked

The argument survives. Its load-bearing claim, that the generated passphrase and not the
KDF carries the security, is arithmetic: 2^120 candidates at any iteration count, even one,
at a fantasy 10^12 guesses per second, is on the order of 10^16 years. Against the
generated passphrase the KDF is genuinely irrelevant and Argon2id would buy nothing that
matters. The availability claim held up in practice during this audit: four independent
PBKDF2s were reachable on this machine without installing anything, which is exactly the
recovery property the document trades for.

The honest weakness is the user-supplied passphrase, and the document names it rather than
hiding it. To put numbers where the document has words: PBKDF2-HMAC-SHA256 at 600,000
iterations costs roughly 1.2 million SHA-256 compressions per guess, which on current
consumer GPUs is on the order of tens of thousands of guesses per second per card. A
40-bit human passphrase falls to one card in months and to a small rig in days; Argon2id
with a memory-hard setting would slow that rig by two to three orders of magnitude. That is
the real price of the availability trade, it is paid only by users who override the
generator, and the document says as much. The mitigation is outside this format: PR 16's
interface should make overriding the generator feel like the downgrade it is. No finding
against the argument itself.

### AES-256-GCM as specified

Sound, and nothing was found. The 12-byte nonce is the GCM-native length, avoiding the
GHASH-derived-IV path entirely. Each archive is a single encryption under a fresh key,
because the 32-byte salt is fresh per archive, so NIST's invocation bounds are not even
approached. Nonce reuse under the same key, the one catastrophic GCM failure, would require
the same salt and the same nonce from the system CSPRNG across two archives, which is not a
probability worth writing down; a repeated nonce alone is harmless because the key under it
differs. The design cannot produce the same nonce twice under the same key unless the
CSPRNG is broken or a writer caches, and the writer rule exists, just in the wrong place,
F25. The AAD binding does what the document says, verified empirically above. The
tag-before-parse rule and the refusal to distinguish wrong-passphrase from tampering are
both correct and correctly explained.

### The minimum iteration floor

The floor is worth keeping and its stated justification is wrong, F26. The claimed attack,
an edited header making an existing archive cheap to crack, is already defeated by the
design itself: salt and iterations feed the key, so an edited value derives a wrong key and
the tag refuses before any plaintext exists. The parameters are implicitly authenticated,
which the document never notices it has achieved. An attacker holding the file cracks at
the cost fixed at encryption time, 600,000, whatever they edit the header to say. What the
floor actually defends is different and real: a nonconforming or malicious writer producing
genuinely cheap archives that conforming readers would otherwise accept silently. The
threshold, 100,000, is defensible for that purpose, since even at the floor a generated
passphrase is untouchable and a human one is not meaningfully more exposed than at 600,000.

The editable header field that genuinely costs a victim something is the one without a
ceiling: `iterations` raised to two billion parks a phone on the KDF for the better part of
an hour before the tag can refuse, with the same "wrong passphrase or altered file" message
at the end of it. A denial of service, not a disclosure, but it is the attack the floor's
paragraph was reaching for, and it is unhandled. F26 proposes the ceiling.

### The generated passphrase

The arithmetic is right and the example is impossible, F23. 120 bits, 24 characters, six
groups of four, all check. But the RFC 4648 Base32 alphabet is `A`–`Z` and `2`–`7`, and
the example `K7M2-9QXP-4RTV-8LZW-3NBY-6HFD` contains `9` and `8`, two of the four digits
the document itself, two lines earlier, correctly says the alphabet excludes. The generator
as specified can never emit this passphrase, and the test vector is built on it.

Outside the format's reach but inside this gate's question: the passphrase's worst enemy is
the screen it is displayed on. A screenshot of the passphrase lands in the photo library
and syncs to iCloud Photos, potentially adjacent to the archive itself in iCloud Drive, one
account compromise away from both halves. A password manager entry is the good outcome, it
is encrypted and it is where a 24-character random string belongs. A paper note is fine. The
format cannot govern this; PR 16's display screen should, by saying where to put it, and
`SECURITY.md`'s backup entry should name the screenshot as the failure mode. Recorded as a
recommendation, not a finding against the document.

### The admitted length leak

The admission is honest and one sentence oversteps it, F28. Payload size is roughly 150
bytes per account, so ciphertext length divided by 150 estimates the account count to
within a card or two, and the same bullet that admits the length leak asserts the archive
"should not reveal how many accounts it holds". Both cannot stand. What padding would buy:
bucketing the plaintext to, say, powers of two would hide the count from the file length,
cost nothing measurable, and, notably, is already possible without a version bump, because
a writer may add an optional padding field that readers ignore under the existing
unknown-fields rule. What it would not buy: invisibility, since the file's existence, name,
and rough size class still show. Agreed with the refusal to pad, for the stated reason that
pretending otherwise is worse; the sentence about account count should be softened to match
the facts, and the additive-padding option is worth a line in the versioning section so a
future writer knows it is open.

## The payload rules

Checked against the gate A1 rule and found correct, as recorded in Verified. The findings
here are edge cases where an implementer must guess, F32: whether `period` on an `hotp`
account or `counter` on a `totp` account is an error or an ignorable irrelevance; whether
`secret` tolerates lower case and internal whitespace, which real exports of other apps
produce; whether an empty `accounts` array is a valid archive; how to report a refused
account that has no `name` or `issuer` to report by; and the JSON number range of
`counter`, which a double-based parser silently truncates above 2^53. Each is one sentence
to pin. None threatens the structure: the never-guess rule contains every one of them,
because the dangerous resolution, inventing a value, is already forbidden.

## Also in scope

**The unencrypted Aegis-compatible export.** The decision is right: a file other apps
import beats a URI list, and one plaintext path is easier to warn about than two. The
defect is that the section specifies nothing, F30: "Aegis compatible JSON" names a format
this document does not define, version, or cite, in a document whose stated purpose is
implementation without trusting the authors. The claim that dropping `otpauth://` loses no
portability is slightly overstated, since the URI is the lingua franca that Aegis JSON
merely contains, but as a file-import path the Aegis format is genuinely the better escape
hatch, and the loss is acceptable and chosen knowingly.

**Refusing Aegis encrypted vaults.** Agreed without reservation. It is the same trade the
KDF section makes, stated in the same direction: scrypt would add a dependency to the most
sensitive path in the app to read a file the user can re-export in plaintext from an app
they still hold. The refusal message naming the workaround is the right shape.

**The versioning rules.** Nearly sufficient, two omissions, F31. The additive boundary is
drawn correctly, and the payload rules quietly make it stronger than the section claims:
a new enumerated value, a future `type` or `algorithm`, is also safe within version 1,
because the never-guess rule makes v1 readers refuse that account loudly while importing
the rest. That deserves to be stated, or a future author will bump the version for a new
account type unnecessarily. The second omission is load-bearing: the guarantee that a file
"cannot be relabelled as a different version and still open" holds only if every future
version binds its own format string as AAD, and the versioning section, which is where a
v2 author will look, never says so. The forever guarantee itself is credible: PBKDF2,
AES-GCM, and JSON are as close to eternal as software gets, and the corrected test vector
pins the rest.

**The threat model of the opening.** Accurate, and unusually honest, with two wording
notes. "The single most dangerous artefact this project produces" is true. "Why the app
generates the passphrase rather than asking for one" reads as though user passphrases do
not exist until the format later allows them; "generates by default" would be exact. And
the metadata bullet's account-count claim is F28. Nothing in the opening is stronger than
the facts beyond those two sentences.

## Findings

Numbered continuing from A2. None are fixed in this gate; it produces a report, and
`docs/BACKUP_FORMAT.md` was deliberately not edited, so the diff between the audited
document and the shipped one stays visible.

### F22: the test vector was derived from the display passphrase, hyphens included, against the document's own rule

What is wrong: the vector's table says the passphrase as fed to the KDF is
`K7M29QXP4RTV8LZW3NBY6HFD`, hyphens stripped, and the normative rule says hyphens are
display only and never passed to the KDF. The published key, ciphertext, and tag were all
produced from `K7M2-9QXP-4RTV-8LZW-3NBY-6HFD`, hyphens included. Established by deriving
both keys with `hashlib`, the OpenSSL CLI, and CommonCrypto, which agree with each other on
both and with the document only on the hyphenated one, and by the published ciphertext
opening under the hyphenated key and refusing under the stripped one, in both Node and
CryptoKit. The "verified independently" paragraph is thereby also false in what it implies:
CommonCrypto, `hashlib`, and Node agreed with each other because all three were handed the
same wrong input; the verification proved consistency, never conformance to the page. Why
it matters: the vector is the one artefact implementers are told to trust over everything,
and it certifies the bug. A reader built to the rule can never open this vector; a reader
built to the vector refuses every archive a rule-following writer produces; both look
finished, and the divergence surfaces at a recovery, which is the one moment this format
exists for. Shipped, this would have been permanent, an ecosystem split baked into version
1. What would fix it: regenerate the vector from the stripped passphrase and re-run the
three-implementation verification with the input checked this time. For cross-checking, the
values this audit derived, from CommonCrypto and `hashlib` and the OpenSSL CLI for the key,
sealed by CryptoKit and independently by Node with byte-identical output: key
`f6e16618648164db0c20f92b2b29e569ff3ff6133aa78b43a3f0ed47984fe0de`, ciphertext
`QBHy/TP6b8OOVzWiAu3nNqPzmP3Uzh5215Iv/ihikzOFWa8t42m/X0koYyYRHi9WCzil+nrnnABMrGbdqjNhKzuvIoxQpDsK/F/RWeAXnbZfr4iPvU/fw5c7ivrQy2ryEQOCSkNXoVmxoCyXXL6eJsUaACdLiw0egWekVYS/Y5gx024u6w60GdpxZ2WCtyk4w4Pre8Mg0g==`,
tag `wKRbIMZZXV0PqfLbWMYdbA==`, all other inputs unchanged. If F23 changes the example
passphrase, regenerate once from the new passphrase instead and these values are cross
checks of the rule, not the final vector.

### F23: the example passphrase cannot be produced by the specified generator

What is wrong: the document specifies the RFC 4648 Base32 alphabet and correctly says it
excludes `0`, `1`, `8`, and `9`; the example and test vector passphrase contains `9` and
`8`. Confirmed against RFC 4648 section 6, fetched today: the alphabet is `A`–`Z` and
`2`–`7`. Why it matters: the example is the specification most implementers will actually
read. A validator written from the example accepts digits the generator never emits; a
validator written from the alphabet, the correct one, rejects the document's own test
vector passphrase at the door, so the two defects compound: F22's vector cannot even be
typed into a strictly conforming reader. It also quietly falsifies the transcription
argument, since the example reintroduces exactly the `8`/`B` confusion the alphabet was
chosen to exclude. What would fix it: a new example drawn from the real alphabet by the
real generator, and the vector regenerated from it, folding this regeneration into F22's.

### F24: passphrase entry is specified by contradiction, and two conforming readers can disagree

What is wrong: three rules interact and no algorithm is given. Generated passphrases are
stripped of hyphens and whitespace and accepted in either case; user passphrases are
verbatim; the file does not record which kind was used, and the single instruction offered,
"a reader must try the passphrase as given", fails every generated passphrase typed the way
the screen displays it. "Accept either case" also never says fold to upper, which is the
only implementable meaning, since the KDF consumes bytes. Why it matters: a reader that
only normalises and a reader that only tries as-given are both defensible readings of this
page, and they open different sets of archives. The user this hits types a correct
passphrase and is told it is wrong, at a recovery, with the original device gone. What
would fix it: one paragraph specifying the trial sequence, try the passphrase exactly as
entered first, and if the tag refuses, try it stripped of whitespace and hyphens and folded
to upper case, then stop; plus vector rows listing typed forms that must open, hyphenated,
lower case, spaced, so the behaviour is certified rather than described.

### F25: the writer's obligations live inside the test vector's caveat

What is wrong: the only statement that salt and nonce come fresh from the system CSPRNG per
archive, never reused, sits in the test vector section as a caveat about the fixed values.
The container section, where an encryptor author reads, specifies formats and lengths but
never generation, freshness, or that a re-export must not reuse a previous archive's
values. Why it matters: nonce reuse is the one mistake that breaks GCM catastrophically,
and the sentence preventing it is in the section an encryptor author has least reason to
study. The design's real protection, fresh salt forcing a fresh key, is also nowhere stated
as an invariant a writer must uphold. What would fix it: a short writing-an-archive
section: 32-byte salt and 12-byte nonce from the system CSPRNG, fresh for every archive
written including re-exports of unchanged accounts, 600,000 iterations, and the floor
binding writers as well as readers.

### F26: the iteration floor's justification claims a defence the tag already provides, and the real editable-header cost is unbounded

What is wrong: the stated attack, an edited header handing a victim a file that is cheap to
crack, cannot occur: salt and iterations feed the key, so any edit derives a wrong key and
the tag refuses before plaintext exists, and an attacker's offline cost is fixed by the
count used at encryption regardless of what the header says. The floor's genuine value,
refusing archives from nonconforming or malicious writers, goes unstated. Meanwhile the
field's actual exploitable direction has no bound: `iterations` edited upward to billions
costs a phone an hour of KDF before the same refusal message, a free denial of service on
exactly the recovery path. Why it matters: this document is normative and its security
arguments will be copied into the implementation's comments and the app's documentation;
gate A2 exists because sentences the artefact cannot back become load-bearing. What would
fix it: state the real rationale for the floor, note that the KDF parameters are implicitly
authenticated, which the design earns and never claims, and give readers licence to refuse
or warn above a generous ceiling, ten million would give writers sixteenfold headroom.

### F27: readers are never told to refuse an unrecognised algorithm or enforce the stated lengths

What is wrong: the refusal rule covers only `format`. Nothing instructs a reader to check
`kdf.algorithm` or `cipher.algorithm` against the expected strings, or to refuse a nonce
that is not 12 bytes or a tag that is not 16, all of which appear only as schema comments.
Why it matters: implicit authentication limits the damage today, but a reader that ignores
the algorithm fields works by accident, a future multi-algorithm reader could be steered by
an edited field toward its weakest supported option, and a library that accepts a 60-byte
nonce will happily run a computation this format never meant. Refuse-loudly is this
document's own standard; it should apply to every field a reader consumes. What would fix
it: one sentence extending the `format` refusal rule to both algorithm strings and the
nonce and tag lengths.

### F28: the metadata bullet claims the archive hides its account count, and the admitted length leak reveals it

What is wrong: "an archive should not reveal how many accounts it holds" and "the only leak
is length" sit in the same bullet, and length divided by roughly 150 bytes per account is
the count. Why it matters: the document's credibility rests on admitting exactly what
leaks; this sentence claims more than the admission supports, the precise failure mode A2
spent eleven findings on. What would fix it: reword to say the length leaks the approximate
account count and nothing else, keep the refusal to pad and its honest reasoning, and note
that padding remains an additive option later, since an optional padding field is ignored
by existing readers under the unknown-fields rule.

### F29: verbatim user passphrases and Unicode, the lockout nobody is warned about

What is wrong: "no Unicode normalisation" is the right spec decision, but a user passphrase
containing non-ASCII can be encoded differently by different keyboards and platforms, NFC
on one, NFD on another, same glyphs, different bytes, different key. The document neither
warns the user-passphrase path about this nor licenses a reader to try normalised variants
on failure. Why it matters: the user affected typed the correct passphrase and is refused,
at recovery time, and the document's own error message tells them the file may be corrupt.
What would fix it: a sentence acknowledging the hazard, and either a recommendation that
writers warn on non-ASCII passphrases or licence for readers to additionally try the NFC
and NFD forms as candidates, which changes no archive bytes and rescues the locked-out
user.

### F30: the Aegis-compatible export is named but never specified

What is wrong: the unencrypted export section names "Aegis compatible JSON" without a
schema, a version, or a citation, in a document whose premise is that formats it emits can
be implemented from the page without trusting the authors. The Aegis vault format is
another project's moving target. Why it matters: the plaintext export is the single most
dangerous file this app will ever write, per this document's own opening, and it is the one
output with no specification at all; an incompatible or half-compatible file discovered at
import time into another app is the same recovery-time failure this whole document exists
to prevent. What would fix it: pin the Aegis vault database version emitted, cite the Aegis
repository's format documentation at a tagged revision, or mark the section non-normative
with a pointer to where PR 16 will specify it, any of the three.

### F31: the versioning section omits the two rules future versions must inherit

What is wrong: the relabelling guarantee depends on every future version binding its own
format string as AAD, and the section governing future versions never states the
obligation; and new values for existing enumerated fields, a future `type` or `algorithm`,
are additive-safe under the payload rules, which the section does not say. Why it matters:
the first omission lets a v2 author silently drop the property this document advertises as
a feature of the design; the second invites an unnecessary version bump, and unnecessary
versions are how forever-formats accumulate readers that open only some files. What would
fix it: two sentences in the changing-this-format section.

### F32: payload edge cases an implementer must currently guess

What is wrong, in one list: `period` on an `hotp` account and `counter` on a `totp`
account, error or ignored, unstated; `secret` case and internal whitespace tolerance,
unstated, while real exports from other apps produce lower case and spaced groups; the
empty `accounts` array, valid or not, unstated; reporting a refused account that has no
`name` or `issuer`, unstated, by index presumably; `counter`'s numeric range, where a
double-based JSON parser silently corrupts values above 2^53, unstated. Why it matters:
every unstated case becomes a per-implementation behaviour, and the never-guess rule's
protection only covers the guesses the document remembered to forbid. None of these can
mis-import an account silently under the current rules, which is why this is one finding
and not five. What would fix it: a sentence each; for `counter`, either a stated bound or a
requirement to refuse values a double cannot represent exactly.

## Positions taken on rejected alternatives

No compression: agreed, the payload is kilobytes and a decompressor on the attacker-facing
path is a bad trade at any size. No key file, hardware key, or split secret: agreed, for a
recovery format every additional factor is an additional way to have no backup. No
timestamp or device name: agreed, and note the filesystem's own metadata leaks creation
time regardless, which is outside the format's reach. No padding: agreed as a default, see
F28 for the sentence it breaks and the additive path it leaves open. Dropping `otpauth://`
plaintext export: agreed, see the Aegis section above. Refusing Aegis encrypted vaults:
agreed without reservation. PBKDF2 over Argon2id: agreed, the argument survives attack and
is the best-reasoned paragraph in the document.

## Unestablished, and what would settle each

- **That the reference implementation's three-way verification was ever run against the
  document's stated input.** This audit's evidence says all three implementations received
  the hyphenated string. Settled by regenerating the vector with the input printed
  alongside each tool's invocation, F22.
- **Which apps genuinely import Aegis plain JSON today.** Asserted by the document and by
  `docs/ROADMAP.md`, not tested here; no Aegis file existed to test with. Settled in PR 16
  by importing a real export into at least one third-party app, and by F30's pinning.
- **The behaviour of any actual implementation.** Nothing exists to audit; every statement
  in this report is about the document. Gate A3 as scoped in `docs/ROADMAP.md` should be
  read as two halves, and this is the first; the PR 16 code needs its own pass against the
  corrected document, including that the implementation strips before deriving, the exact
  bug the current vector would have certified as correct.
- **CommonCrypto and CryptoKit sharing corecrypto.** The document counts them within
  "three implementations sharing no code"; both sit on Apple's corecrypto, though for
  different primitives here, so each operation still had two independent implementations.
  Unresolved because it is wording, not cryptography; the regeneration should just claim
  the pairing accurately.

Housekeeping, unnumbered: `SECURITY.md`'s "All cryptography comes from CryptoKit" becomes
false when PR 16 uses CommonCrypto for PBKDF2, which CryptoKit does not provide; amend it
the same day. The opening's "generates the passphrase rather than asking for one" should
say "by default". And PR 16's passphrase display screen should tell the user where the
passphrase belongs, a password manager or paper, and that a screenshot puts it in iCloud
Photos beside the archive it protects.

The bottom line restated: the design is sound, the arguments hold, and the two blocking
findings are exactly the kind of defect this gate was scheduled to catch, wrong bytes in
the one artefact that would have made the wrongness permanent. Fix the vector, specify the
entry algorithm, and freeze it.
